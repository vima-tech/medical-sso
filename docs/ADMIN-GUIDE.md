# 统一身份管理员操作指南

## 管理边界

统一身份管理平台（`18081` 的 `/admin`）负责：机构与科室、人员账号与密码、统一人员标识、通用身份、可访问的业务系统、业务系统登记。日常操作全部在这里完成。

业务系统负责：菜单、按钮、岗位、病区、处方、数据范围等业务权限。

Keycloak 是底层的认证引擎，负责签发令牌、校验密码、维护会话。它自带的控制台面向 IAM 工程师，**不作为日常运维界面**，只在引擎故障排查时由平台负责人使用，并限制在管理网段访问。

界面上不会出现 Realm、Client、Scope、Mapper 这类术语，对照关系见 README 的术语表。

日常运维所需的全部操作都已在管理平台内：机构与科室、人员管理（含批量导入）、授权中心（含按科室批量授权）、业务系统、通用身份、审计记录。

## 账号与登录入口

都从 `18081` 进，系统按角色自动分流，不需要记路径。

| 账号 | 登录 18081 后落到 | 用途 |
| --- | --- | --- |
| 平台管理员 `sso-admin` | 统一身份管理平台 | 机构科室、人员管理、业务系统登记 |
| 业务人员，例如 `zhangsan` | 应用门户 | 点进本人有权使用的业务系统 |
| 认证内核引导管理员，`deploy/.env` 里的 `admin` | 没有界面可登录 | 控制台已关闭，仅供底层排查时经 Admin API 使用 |

**第一次登录**：账号 `sso-admin`，初始密码 `Admin@123456`。登录后系统会立刻要求改密码——初始密码写在配置文件里、人人可见，所以它只能用一次。改完就进入管理平台。

（本机演示环境例外：`seed-demo.sh` 会把密码重置为 `deploy/.env` 里的 `SSO_PLATFORM_ADMIN_PASSWORD` 并取消强制改密，方便反复演示。）

管理平台顶栏有「应用门户」入口，门户顶栏对管理员显示「身份管理平台」入口，两边可互相切换。

`deploy/.env` 里的 `admin` 属于 `master` Realm，用它登录业务登录页会提示「工号或密码错误」，这是预期行为——它不是业务账号。

平台管理员由 `sso-platform-admin` 角色决定，权限高于机构管理员，按最小范围授予。演示数据里 `zhangsan` 是医生，不带这个角色。

## 一、业务系统

推荐在门户里完成，不需要进 Keycloak 管理台。

用具有 `sso-platform-admin` 身份的账号登录管理平台，进「业务系统」，点「登记业务系统」。只填四项：

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| 系统名称 | 住院医生工作站 | 展示名称 |
| 系统编码 | `his-web` | 小写字母、数字和中划线，登记后不可更改 |
| 系统访问地址 | `https://his.intra.example` | 浏览器访问该系统的地址，协议和域名必须与实际一致 |
| 接入方式 | Spring Boot 2.x / JDK 8 | 决定生成哪一套对接说明 |

提交后自动建立客户端、强制 PKCE、推导回调地址、创建 `access` 角色，并给出该系统专属的对接文档。

Client Secret 只显示这一次，请立刻复制交给业务系统负责人并存入密钥系统。遗失后可在系统详情页重新生成；重新生成会立即使旧 Secret 失效，业务系统配置必须同步更新。

登记完成后还要给用户分配该系统的 `access` 角色，见第四节，否则用户能登录但进不去。

`sso-platform-admin` 是平台级角色，能创建 OAuth 客户端并取得 Client Secret，权限高于机构管理员 `organization-admin`，只授予统一认证平台的负责人，不要按机构批量发放。两个角色不要合并。

系统访问地址填错是最常见的问题：它决定回调地址，与浏览器实际使用的地址不一致时会一直跳回登录页。

## 二、机构与科室

在管理平台的「机构与科室」中维护，不需要进 Keycloak 控制台。

先新增机构（名称 + 机构编码），再在机构卡片上点「新增科室」加科室（名称 + 科室编码）。人员建档时的机构、科室下拉就来自这里，科室随机构联动。

编码全局唯一，会写进人员身份信息并下发给各业务系统，建档后不建议更改；重复编码在保存时会被拦下并提示被谁占用。

删除有两层保护：机构下还有科室时不允许删除；机构或科室下还有人员时不允许删除，并提示还有多少人。要撤销一个科室，先把该科室的人员调整到别处。

## 三、人员管理

用具有 `sso-platform-admin` 身份的账号登录管理平台，进「人员管理」。日常人员操作全部在这里完成，不需要打开 Keycloak 控制台。

新增人员只填这几项：

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| 姓名 | `张三` | 中文全名，姓在前。它就是各业务系统显示的姓名 |
| 工号 | `10086` | 全局唯一，重复会被拦下 |
| 登录名 | `zhangsan` | 建档后不可修改 |
| 统一人员标识 | `P000123` | 跨系统关联本人的唯一标识，全局唯一 |
| 所属机构 | 下拉选择 | 选项来自机构科室目录，不需要记编码 |
| 所属科室 | 下拉选择 | 随机构联动，只显示该机构下的科室 |
| 通用身份 | 医生 / 护士 | 跨系统通用身份 |
| 可访问的业务系统 | 勾选 | 勾了才能进入对应系统 |
| 初始密码 | | 建议勾上「要求首次登录修改密码」 |

统一人员标识和工号都会查重，被占用时会明确提示被谁占用。人员错绑的代价很高，不要绕过这个校验。

初始密码和重置后的密码请当面或通过安全渠道交给本人，不要用微信或短信发送。

停用人员：在列表点「停用」。停用会同时注销该人员当前所有登录会话。已经建立的业务系统本地 Session 不受影响，重要系统仍需按第十节处理。

## 四、通用身份与系统授权

角色分两层，都在「人员管理」的编辑页里勾选，不需要理解 Keycloak 的角色模型。

**通用身份**：跨系统的身份，例如医生、护士、机构管理员。业务系统据此判断岗位。

**可访问的业务系统**：勾选后本人才能进入对应系统；未勾选的系统会在登录后返回 403。系统内部的菜单、病区、数据范围等权限仍由各业务系统自己管理，统一认证不介入。

`sso-platform-admin` 是平台级身份，能登记子系统、创建 OAuth 客户端并取得 Client Secret，只授予统一认证平台的负责人。

修改角色后不会立即影响已签发的 Token 和业务系统本地 Session，需要本人重新登录才生效。

## 五、授权中心

「人员 × 业务系统」的矩阵视图。左侧下拉按科室筛选，勾选后点保存即生效。

点列头的「全选/全不选」可对当前列表里的所有人整列授权或收回，这就是按科室批量授权：先在下拉里选中科室，再点该系统的列头即可。

保存只影响当前页面上列出的人员，不会动到其他科室，因此可以放心按科室分批处理。

## 六、批量导入人员

人员管理右上角的「批量导入」。先下载 CSV 模板，用 Excel 或 WPS 填好后另存为 CSV 再上传。

逐行导入，一行填错不影响其他行；导入后会按行号给出回执，说明每一行成功还是失败、失败原因是什么。修正后重新导入即可，已成功的行会因为工号和统一人员标识查重被自动跳过，不会重复建档。

机构编码和科室编码必须是「机构与科室」里已存在的编码，且科室要属于该机构。

## 七、审计记录

分「登录记录」和「管理操作」两类。登录记录含登录成功、失败、退出和改密，可按类型筛选；管理操作记录管理员在平台上做过的全部增删改。

记录只读，管理员无法删改，保留 30 天后由系统自动清理。管理操作不记录请求体，避免把密码等内容写进审计库。

要查某人当前在哪些设备上登录着，在「人员管理」里打开该人员的编辑页，底部有「在线登录」，并可一键强制在所有设备下线。

## 八、登录页与界面语言

登录页由本项目自己的主题完全接管，不使用 Keycloak 自带的页面结构和样式。改文案和改样式都在这一个目录里：

```text
deploy/keycloak/themes/medical-union/login/
├── template.ftl                       页面外壳：品牌区、卡片、页脚
├── login.ftl                          登录表单
├── login-update-password.ftl          首次登录设置新密码
├── messages/messages_zh_CN.properties  全部界面文案
└── resources/css/medical-login.css     全部样式
```

改文案只需要动 `messages_zh_CN.properties`，例如把「工号或登录名」改成本院的叫法。改配色改 `medical-login.css` 顶部的一组变量。**改完必须重启 Keycloak 容器**，模板和样式在启动时加载。

没有单独覆盖的页面（错误页、会话过期页等）会自动沿用 `template.ftl` 的外观，不需要逐个改。

Realm 只开放中文（`supportedLocales` 仅 `zh-CN`），登录页因此没有语言切换控件。需要支持第二种语言时，在 Realm 的语言设置里加上，并在 `messages` 目录下补对应的文案文件。

Realm 的语言设置由 `deploy/keycloak/realm/medical-realm.json` 提供，随导入生效，不需要手工配置。

## 九、认证内核的边界

Keycloak 只作为认证内核运行在网关后面，**不对外暴露端口，自带的管理控制台已用 `--features-disabled=admin` 在引擎层面移除**。整套系统对外只有统一身份管理平台一个入口，不存在第二个管理界面。

因此不再有「进 Keycloak 后台手工建客户端」这条路。业务系统一律在第一节的登记页建立，登记时会自动完成客户端创建、强制 PKCE `S256`、回调地址推导、`medical-profile` Scope 挂载和 `access` 角色创建——这些正是过去手工建客户端最容易漏的步骤。

需要底层排查时（例如认证内核起不来、Realm 导入失败），用容器日志和 `deploy/.env` 里的引导管理员经 Admin API 处理：

```bash
docker compose logs keycloak            # 引擎日志
docker compose exec keycloak /opt/keycloak/bin/kc.sh show-config
```

这属于运维动作，不是日常管理手段。任何需要反复手工进内核操作的场景，都应该反馈成管理平台的功能缺口。

## 十、停用与离职

停用人员时：

1. 在「人员管理」里点该人员的「停用」。停用会自动注销他的全部在线登录，不需要额外操作。
2. 如需保留账号但立即断开，在该人员的编辑页用「强制在所有设备下线」。
3. 通知高风险业务系统终止对应 `person_id` 的本地 Session——业务系统自己建立的会话不受统一认证控制。

只删除角色不能保证已经签发的 Token 和本地 Session 立即失效。

## 十一、生产审计建议

生产环境启用登录事件和管理员事件，至少保留：登录成功、登录失败、退出、用户变更、角色变更、Client 变更。日志进入内网日志平台，限制访问并设置保留周期。

Token 和日志中不得写入患者资料、病历内容、身份证号、诊断信息等敏感业务数据。
